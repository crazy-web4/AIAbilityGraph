### 赛道选择的六个问题

| 问题 | 评估要点 |
|------|---------|
| **1. 痛点够痛吗？** | 用户愿意为解决这个问题付多少钱？ |
| **2. 时机对吗？** | 模型能力是否已到临界点？市场教育成本如何？ |
| **3. 你有不公平优势吗？** | 数据/行业认知/技术/渠道/人脉 |
| **4. 能形成网络效应吗？** | 用户越多产品越好吗？数据飞轮能转起来吗？ |
| **5. 商业模式可持续吗？** | LTV > 3×CAC？毛利率 > 50%？ |
| **6. 防御壁垒在哪里？** | 巨头进场后你能活下来吗？ |

### MVP 的技术选择原则

```
┌─────────────────────────────────────────────────────────────────┐
│                  MVP 技术选型原则                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. 用 API，不要自训练模型                                        │
│     → GPT-4o / Claude 3.5 API 足够验证任何应用层想法              │
│     → 自训练模型的 MVP 至少需要 3-6 个月                          │
│                                                                  │
│  2. 用现成框架，不要自研                                          │
│     → LangChain / Dify / Next.js 等成熟框架                      │
│     → 把时间花在核心差异化逻辑上                                   │
│                                                                  │
│  3. 用云服务，不要自建基础设施                                   │
│     → Vercel / Railway / Supabase                                │
│     → 用户量验证后再考虑成本优化                                   │
│                                                                  │
│  4. 先跑通流程，再优化效果                                        │
│     → 先有 60 分的产品，再迭代到 90 分                             │
│     → 完美主义是 MVP 的敌人                                      │
│                                                                  │
│  5. 可替换性优先                                                  │
│     → 抽象接口，方便未来替换底层模型                               │
│     → 不要和任何一家 API 深度绑定                                  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### MVP 快速技术栈推荐

```yaml
推荐 MVP 技术栈（2 周可上线）:
  前端: Next.js + Tailwind CSS + shadcn/ui
  后端: Next.js API Routes 或 FastAPI
  大模型: GPT-4o-mini（验证期）→ GPT-4o（正式版）
  数据库: Supabase (PostgreSQL + Auth)
  向量存储: pgvector（和 PG 一起，零额外运维）
  文件存储: Supabase Storage 或 S3
  支付: Stripe（海外）/ 微信+支付宝（国内）
  部署: Vercel（前端）+ Railway/Fly.io（后端）
  监控: Sentry + PostHog（免费层）
  邮件: Resend / SendGrid
  
月成本估算: $50-200（用户 < 1000 时）
```

### 如何判断 PMF（Product-Market Fit）

| 信号 | 强 PMF | 弱 PMF | 无 PMF |
|------|--------|--------|--------|
| **用户增长** | 口碑传播，自然增长 | 需要付费获客 | 花钱也没人用 |
| **留存率** | D7 > 40%, D30 > 20% | D7 20-40% | D7 < 20% |
| **付费意愿** | 用户主动问付费方案 | 需要推销 | 免费也不愿意用 |
| **NPS 分数** | > 50 | 30-50 | < 30 |
| **用户反馈** | "这个产品太需要了！" | "还行，可以试试" | "我不需要这个" |
| **Sean Ellis 测试** | >40% 说"非常失望" | 20-40% | <20% |

### 投资人常见问题

```
Q1: "如果 OpenAI/Google 做了同样的功能，你怎么办？"
→ 回答要点：
  - 你的独特壁垒（数据/行业/集成深度）
  - 大公司的优先级（他们不会做所有细分市场）
  - 执行速度优势（大公司决策慢）

Q2: "你的技术护城河是什么？"
→ 回答要点：
  - 不要说"我们的模型更好"（容易被替代）
  - 强调数据飞轮、行业集成、用户网络
  - 展示竞争壁垒的可量化指标

Q3: "大模型能力越来越强，你的价值会不会被压缩？"
→ 回答要点：
  - 模型能力提升 = 你的产品也变好
  - 价值在于应用层 + 行业理解 + 数据积累
  - 类比：操作系统变强 ≠ 应用开发者没价值

Q4: "你的获客成本（CAC）和用户生命周期价值（LTV）是多少？"
→ 回答要点：
  - 给出具体的数字和趋势
  - LTV/CAC > 3 是健康标准
  - 说明获客渠道和优化方向
```

### 十大常见失败原因

| 排名 | 失败原因 | 案例 | 教训 |
|------|---------|------|------|
| **1** | **没有真实需求** | 大量"AI + X"套壳应用 | 先验证痛点再写代码 |
| **2** | **技术依赖风险** | 纯调 GPT API 的产品 | 建立数据和行业壁垒 |

| **5** | **获客成本过高** | 大量烧钱投放但留存低 | 产品驱动增长优先 |
| **6** | **团队不合** | 技术+商业创始人分歧 | 提前约定股权和决策权 |
| **7** | **合规风险** | 医疗/金融 AI 未获认证 | 提前规划合规路径 |
| **8** | **数据质量问题** | 训练数据偏差导致事故 | 投入数据质量管控 |
| **9** | **过度融资** | 估值过高后续融资困难 | 控制估值，保持增长节奏 |
| **10** | **时机错误** | 太早（技术不成熟）或太晚（红海） | 关注技术拐点信号 |

```
Month 9-12:
├── 融资：天使轮 ¥500 万
├── 团队扩展到 8 人
├── 增加功能：合同模板生成 + 法律问答
├── 付费用户 200+，MRR ¥300,000
└── NPS 65（强 PMF 信号）

关键成功因素：
1. 创始团队有法律背景 → 深度理解行业痛点
2. 数据飞轮 → 准确率持续提升，竞品追赶困难
3. ToB 模式 → 高客单价（¥5,000-20,000/月），高留存
4. 垂直深耕 → 通用模型做不到的法律专业度
```

### 案例二：AI 教育产品 Pivot 经历

```
背景：2 人技术团队，想做"AI 版家教"

Pivot 1: 通用 AI 家教（失败）
├── 产品：学生上传问题 → AI 讲解答案
├── 问题：
│   - ChatGPT 可以直接做到
│   - 学校禁止使用（防作弊）
│   - 获客成本高（家长不信任新品牌）
└── 结果：3 个月，500 用户，留存 < 10%

Pivot 2: 教师备课助手（成功）
├── 洞察：和老师聊天发现，备课是最大的痛点
├── 产品：
│   - AI 生成教案 + 课件 + 练习题
│   - 按课标对齐，支持不同教材版本
│   - 教师社区分享和评价
├── 结果：
│   - 6 个月，5000+ 教师用户
│   - 留存 45%（D30）
│   - 学校团体采购 → MRR ¥150,000
└── 壁垒：
    - 教案数据库（2 万+ 高质量教案）
    - 教师社区（网络效应）
    - 课标对齐数据（合规壁垒）

教训：
1. ToC 教育产品获客太难 → 转 ToB（学校/机构）
2. 学生端产品有合规风险 → 教师端更安全
3. Pivot 不丢人 → 快速调整方向是创业核心能力
```

### 案例三：独立开发者的 AI 产品之路

```
背景：1 人全栈开发者，业余时间做 AI 产品

产品：AI 代码审查工具（Chrome 插件 + API）

技术栈：
├── 前端：Chrome Extension + React
├── 后端：FastAPI + Railway
├── 模型：GPT-4o-mini（代码审查） + Claude 3.5（复杂分析）
├── 数据库：Supabase
└── 支付：Stripe

开发周期：4 周（业余时间）

增长策略：
├── 在 GitHub/Hacker News 发布 → 首日 200 用户
├── 写技术博客分享开发过程 → 带来持续 SEO 流量
├── Twitter/X 上展示 Demo → 开发者社区传播
└── Product Hunt 发布 → 获得 "Product of the Day"

收入：
├── 免费层：每月 50 次代码审查
├── Pro 层：$19/月，无限审查
├── Team 层：$49/月/人，团队协作功能
├── 6 个月后：800+ 付费用户，MRR $15,000
└── 年化 ARR ≈ $180,000（作为副业非常可观）

关键经验：
1. 选一个小而具体的场景（代码审查，不是"AI 编程"）
2. 利用开源社区做增长（GitHub 是最好的获客渠道）
3. Freemium 模式在开发者工具中效果最好
4. 一个人也能做出盈利的 AI 产品
```

## 🏁 结语

**AI 创业的本质是在技术变革浪潮中找到自己的位置**：
1. 大模型是基础设施，不是产品 —— 你需要在模型之上创造独特价值
2. 技术壁垒在弱化，数据和行业壁垒在强化 —— 选择正确的护城河
3. 速度是最大的优势 —— 在大公司反应过来之前建立领先地位
4. 失败是常态 —— 快速验证、快速调整、快速学习

**给创业者的最后建议**：

> "不要问 AI 能做什么，要问用户的痛点是什么。最好的 AI 产品，用户甚至不知道背后用了 AI —— 他们只知道问题被完美解决了。"
