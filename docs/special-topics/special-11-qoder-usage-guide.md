## 1. Qoder 是什么

Qoder 是一款 **Agentic Coding IDE（智能体式编程集成开发环境）**。它不只是"能补全代码的编辑器"，而是把一个大模型 Agent 深度嵌入到开发流程里：能读你的整个仓库、能调用工具执行命令、能记住项目约定、能自主拆解并完成多步骤任务。

它的能力大致分三层：

| 层次 | 能力 | 你感知到的形态 |
|------|------|---------------|
| **理解层** | 语义检索、符号索引、Repo Wiki、Memory | 问"这个功能在哪实现"能直接答对 |
| **执行层** | 文件读写、终端命令、浏览器自动化、调试 | 让它改代码 / 跑测试 / 起服务，它自己动手 |
| **扩展层** | Skills、MCP、Subagent | 用技能包和外部工具把能力延伸到任意领域 |

**核心理念**：你负责"意图和验收"，Qoder 负责"检索、规划、执行、验证"。用好它的关键，是把上下文喂准、把任务描述清楚、把边界设定明确。

## 2. 五种交互模式

Qoder 提供多种模式，对应不同的工作阶段。理解它们的分工，是用好 Qoder 的第一步。

### 2.1 Agent 模式（默认）

拥有全部工具权限，可以直接修改文件、执行命令。适合**目标明确、要动手实现**的任务：写功能、改 bug、重构、跑脚本。

> 场景：`把 docs/special-topics 里所有文档的 AI 腔清洗一遍` —— Agent 会自己检索、逐个改写、验证。

### 2.2 Plan 模式（规划）

**只读**模式，用于在动代码前设计方案。它会先探索仓库、权衡多种实现路径、产出一份可评审的实施计划，你确认后再切回 Agent 执行。

适合：架构决策、大范围重构、需求模糊需要先探索的任务。

> 场景：`给项目加一套文档自动化校验` —— 先用 Plan 模式讨论"用 pre-commit 还是 CI，检查哪些规则"，定稿后再执行。

### 2.3 Ask 模式（问答）

**只读**模式，纯粹回答关于代码/架构的问题，不做任何修改。适合快速理解陌生代码库。

> 场景：`这个项目的 examples 目录是怎么组织的？check_examples.py 做了什么？`

### 2.4 Debug 模式（调试）

系统化的排障模式：基于运行时证据（日志、报错、复现步骤）定位 bug 根因，而不是靠猜。适合"某处报错/行为异常/性能下降"的排查。

### 2.5 Quest 模式（自主任务）

把一个大任务整体交给 Agent，它自主规划、分步执行、自我验证，中途按检查点向你汇报。适合耗时较长、步骤较多、可以"托管"的任务。详见 [第 6 节](#6-quest-mode把任务交给-agent-自主完成)。

**模式选择建议**：

```
需求模糊 / 影响面大  → 先 Plan，定稿后 Agent
只想理解代码          → Ask
报错 / 异常 / 变慢    → Debug
目标明确的动手活      → Agent
步骤多、可托管的大活  → Quest
```

## 3. 基础用法：对话与内联编辑

### 3.1 对话面板（Chat）

- 直接用自然语言描述需求，中英文均可。
- **引用上下文**：用 `@` 提及具体文件、符号、目录，把上下文精确地喂给模型，比让它自己满仓库找更快更准。
- **粘贴报错**：把完整堆栈直接贴进来，比"它报错了"这种描述有效得多。

### 3.2 内联编辑（Inline Edit）

在编辑器里选中一段代码，唤起内联对话框，直接说"把这段改成异步的""给这个函数补类型注解"。改动只作用于选中范围，适合**小而精准**的局部修改。

### 3.3 代码补全

Qoder 在输入时给出行级/块级补全建议，`Tab` 采纳。补全会结合当前文件上下文和仓库约定，倾向于生成"和周围代码风格一致"的内容。

### 3.4 描述任务的黄金结构

一个好指令通常包含四要素：

```
【目标】我要做什么
【范围】涉及哪些文件/模块
【约束】必须遵守的规则（风格、依赖、不能动的地方）
【验收】怎样算完成（测试通过、格式符合、能跑起来）
```

> ❌ 差：`优化一下代码`
> ✅ 好：`把 scripts/check_examples.py 里重复的路径拼接逻辑抽成一个函数，保持现有 CLI 参数不变，改完运行 python scripts/check_examples.py 确认输出和之前一致`

## 4. 上下文工程：如何让 Qoder "看懂"你的仓库

Qoder 回答质量的上限，取决于它拿到的上下文。以下几种机制协同工作：

### 4.1 语义检索（Codebase Search）

按"含义"而非"精确文本"检索代码。你问"认证逻辑在哪"，它能定位到相关实现，即使代码里没有"认证"两个字。

### 4.2 符号索引（Symbol Index）

对类名、方法名、变量名做精确索引，并能查它们的调用关系（谁调用了它、它调用了谁、继承/实现关系）。查具体符号时比语义检索更准。

### 4.3 精确文本检索（Grep）与文件匹配（Glob）

- Grep：基于 ripgrep 的正则全文搜索，适合找确切字符串、日志文案、配置项。
- Glob：按文件名模式找文件，如 `**/*keypoints.md`。

### 4.4 项目规则文件：AGENTS.md / CLAUDE.md

仓库根目录的 `AGENTS.md`、`CLAUDE.md` 是给 Agent 看的"项目说明书"。本项目的 `AGENTS.md` 就规定了：

- 教程的章节结构（第 1–7 章）
- 内容质量标准（理论 + 代码 + 实战）
- 代码示例规范（Python、可运行、PyTorch 生态优先）
- 文档结构模板（学习目标 / 核心概念 / 代码示例 / 常见误区 / 练习题）

**建议**：把你希望 Agent 长期遵守的项目约定写进 `AGENTS.md`，它每次都会读到，比在对话里反复叮嘱有效。

### 4.5 上下文优先级

当多个信息源冲突时，Qoder 遵循：

```
用户当前指令 > 代码/配置的事实 > 上下文推断结论 > 规则/技能 > 记忆
```

即：**你现在说的**永远最高优先，其次是**代码里实际写的**。

## 5. Repo Wiki：自动生成的仓库知识库

Repo Wiki 是 Qoder 对整个仓库进行分析后自动生成的**结构化知识文档**，包括：

- 项目整体架构与模块划分
- 每个模块的职责、关键文件、依赖关系
- 技术栈、编码约定、常用命令

**用法**：

1. 在 Qoder 中打开 Repo Wiki 面板，触发对当前仓库的索引与生成。
2. 生成后，它成为一份"活文档"，随代码演进可增量更新。
3. 新成员 onboarding、接手陌生项目时，先读 Repo Wiki 快速建立全局认知。

**对本项目的价值**：AIAbilityGraph 有 `docs/`（教程正文）、`examples/`（配套代码）、`presentation/`（网页讲义）、`Aliyun-acp/`（认证镜像）等多个平行目录。Repo Wiki 能一眼讲清它们的关系，省去逐目录翻找。

## 6. Quest Mode：把任务交给 Agent 自主完成

Quest Mode 面向**可以托管的中大型任务**。与逐条对话不同，你把一个完整目标交给它，它会：

1. **理解与规划**：拆解任务、列出步骤（Todo）。
2. **自主执行**：逐步调用工具——读文件、改代码、跑命令、验证结果。
3. **检查点汇报**：在关键节点或需要决策时向你确认。
4. **自我验证**：完成后跑测试/构建，确认达到验收标准。

**适合 Quest 的任务**：

- 批量重构（如"把全项目 print 调试替换为 logging"）
- 成体系的文档补全（如"给 examples 下所有脚本补齐 README"）
- 迁移类工作（如"把 requirements 从旧依赖升级到新版并修复兼容性"）

**用好 Quest 的关键**：

- 开头把**验收标准**说清楚，它才知道何时算完成。
- 明确**边界**：哪些文件不能碰、哪些决策要先问你。
- 复杂任务先让它出 **Plan/Todo**，你审一遍再放行执行。

## 7. Memory 记忆系统

Memory 让 Qoder 跨会话记住**你的偏好**和**项目的约定/经验**，不必每次重新交代。

### 7.1 记忆类别（节选）

| 类别 | 记什么 |
|------|--------|
| `user_info` / `user_hobby` | 你的身份、兴趣 |
| `user_communication` | 你希望它怎么说话（语气、详略） |
| `user_behavior` | 你希望它怎么做事（如"完成前先自检"） |
| `project_*` | 项目技术栈、构建/依赖配置、架构、环境 |
| `development_*` | 代码规范、实践规范、测试规范、注释规范 |
| `*_experience` | 工具/技能/任务经验、常见坑、关键决策 |

### 7.2 触发记忆

- **显式**：你说"记住，本项目所有文档用中文写""以后改代码前先跑测试"——它会持久化。
- **隐式反思**：当它发现可复用的经验或踩到坑时，会主动沉淀为记忆。

### 7.3 使用与维护

- 记忆是**辅助**，不替代当前指令和代码事实；使用前会校验其时效性。
- 发现记忆过时/错误，直接说"那条记忆不对了，改成……"，它会更新或删除。
- 一次记忆 = 一个主题，避免重复堆积。

> 本项目可沉淀的记忆示例：`docs 每章含 README + 主文档 + *-keypoints.md`、`代码示例统一放 examples/，用 Python + PyTorch`、`番外篇按 Special-NN 编号并登记到两个 README`。

## 8. Skills 技能系统

Skills 是**封装好的专项能力包**：一个技能 = 一份教 Agent 如何完成特定任务的说明书（`SKILL.md`）+ 可选脚本/资源。

### 8.1 本项目已装载的部分技能

| 技能 | 用途 |
|------|------|
| `agent-browser` / `playwright` | 浏览器自动化：导航、填表、点击、截图、爬取、测网页 |
| `audit-website` | 网站 SEO/性能/安全/内容审计（230+ 规则） |
| `frontend-design` / `web-design-guidelines` | 高质量前端界面设计与 UI 规范审查 |
| `pptx` / `docx` / `xlsx` / `pdf` | 生成/读取/编辑 Office 文档与 PDF |
| `technical-writer` | 写文档、API 参考、教程、README |
| `firecrawl-search` | 联网搜索 + 全文抽取 |
| `brainstorming` | 创作前的需求/设计探索 |
| `systematic-debugging` / `diagnosing-bugs` | 系统化排障 |
| `tdd` / `test-driven-development` | 测试驱动开发 |
| `project-analysis` | 逆向理解陌生代码库、做架构 onboarding |
| `archify` | 生成架构/流程/时序/状态图（可交互 HTML） |
| `lark-*` 系列 | 飞书文档/表格/日历/邮件/多维表格等操作 |

### 8.2 如何调用技能

- **斜杠命令**：输入 `/技能名`（如 `/commit`、`/technical-writer`）。
- **自然语言触发**：描述需求，命中技能触发条件时 Qoder 自动调用。例如说"帮我把这份内容做成 PPT"，会触发 `pptx`。

### 8.3 创建自定义技能

用 `create-skill` 技能可以引导你把重复性工作流沉淀成自己的技能，之后一句话即可复用。

> 对本项目：`pptx` + `presentation/` 目录配合，可把教程章节转成网页讲义/幻灯片；`technical-writer` 适合批量产出规范文档。

## 9. MCP 与外部工具集成

**MCP（Model Context Protocol）** 是让 Qoder 连接外部工具/数据源的标准协议。通过 MCP Server，Agent 能操作数据库、浏览器、飞书、Sentry、GitHub 等外部系统。

### 9.1 工作方式

1. 配置 MCP Server（在 Qoder 设置中添加）。
2. Qoder 发现该 Server 提供的工具及其参数 schema。
3. 需要时按 schema 调用工具，拿到结果继续推理。

### 9.2 典型 MCP 场景

- **数据库**：查表结构、跑只读查询辅助排障。
- **浏览器**：抓取实时网页、验证前端渲染效果。
- **协作平台**：飞书/Slack 读写文档、发消息、查日程。
- **可观测性**：Sentry 拉取线上错误、汇总近期异常。

> 使用要点：调用外部工具前，Qoder 会先读取该工具的参数定义，避免猜参数；涉及写操作/风险操作时会先与你确认。

## 10. Subagent 子智能体

对于**独立、可并行、需要跨多文件阅读**的子任务，Qoder 可以派发专门的子智能体（Subagent）去做，主线程只保留结论，不被中间过程的文件内容淹没。

内置子智能体类型：

| 类型 | 职责 |
|------|------|
| **Browser** | 在浏览器里执行操作：点击、输入、导航、截图、爬数据、测网页 |
| **CodeReview** | 对代码改动做专业评审，聚焦逻辑 bug 与安全问题（需显式请求） |
| **ComputerUse** | 操作本地桌面应用：点击、输入、拖拽、按键 |

**用法示例**：

- `起个子智能体打开本地预览页面，截图确认排版没问题` → Browser
- `帮我 review 这次改动` → CodeReview
- 多个互不依赖的检索/分析任务 → 并行派发多个子智能体，同时跑。

## 11. 终端、预览与调试

### 11.1 终端执行

Qoder 可在终端跑命令（`git`、`npm`、`python`、`docker` 等）：

- **前台执行**：等待命令结束拿输出（如跑测试）。
- **后台执行**：长任务/常驻进程（如起开发服务器），返回 terminal id，可随时查看输出。
- **安全边界**：默认不擅自执行破坏性命令（删库、force push 等），也不擅自 `git commit`——除非你明确要求。

### 11.2 Web 预览

起了本地 Web 服务后，Qoder 可开一个预览浏览器，你能直接交互，页面 DOM 也能回传给它做分析。本项目的 `presentation/index.html` 讲义就适合这样预览。

### 11.3 问题诊断

`GetProblems` 能拉取文件的编译/lint 报错，和你 IDE 里看到的一致。改完代码让它自查问题，是收尾的好习惯。

## 12. 典型工作流实战

以下用本项目（AIAbilityGraph）的真实场景演示端到端用法。

### 工作流 A：新增一篇番外篇文档（本指南就是这么做的）

```
1. 【Ask/检索】先读 docs/special-topics/README.md，确认现有编号到 Special-10
2. 【Agent】新建 special-11-xxx.md，按番外篇模板组织内容
3. 【Agent】在 special-topics/README.md 目录表 + 内容概览登记
4. 【Agent】在 docs/README.md 番外篇速览表登记
5. 【验证】检查三个文件的链接与编号一致
```

要点：**先摸清约定（编号规则、登记位置），再动手**，避免破坏文档体系的一致性。

### 工作流 B：批量校验 examples 代码示例

```
1. 【Ask】读 scripts/check_examples.py，理解现有校验逻辑
2. 【Plan】设计要补的校验规则（语法、依赖、引用完整性）
3. 【Agent/tdd】先把规则写成回归测试，再改脚本
4. 【终端】python scripts/check_examples.py 跑一遍
5. 【Debug】对失败项逐个定位修复
```

### 工作流 C：把教程章节转成网页讲义

```
1. 【frontend-design 技能】确定视觉风格
2. 【Agent】读 presentation/ 现有结构，按章节生成页面
3. 【终端 + 预览】起本地服务，预览排版
4. 【Browser 子智能体】截图确认各章节渲染正常
```

### 工作流 D：接手陌生仓库快速上手

```
1. 【Repo Wiki】生成仓库知识库，建立全局认知
2. 【project-analysis 技能】系统化梳理架构、启动流程、核心链路
3. 【Ask】针对具体模块提问，深入细节
```

## 13. 最佳实践与避坑清单

### ✅ 推荐做法

1. **上下文喂准**：用 `@` 引用具体文件/符号，比让模型满仓库找更快更准。
2. **先规划后执行**：影响面大的改动，先 Plan 模式定方案，再 Agent 执行。
3. **说清验收标准**：明确"怎样算完成"，Agent 才知道何时收手、如何自验。
4. **把约定写进 AGENTS.md**：长期规则写进规则文件，一次配置长期生效。
5. **善用记忆**：反复要交代的偏好，让它"记住"，跨会话复用。
6. **改完自查**：让 Qoder 跑测试 / `GetProblems`，把验证纳入闭环。
7. **大任务托管 Quest，小改动用内联**：按任务粒度选对交互方式。

### ❌ 常见坑

1. **指令太笼统**：`优化一下` 这种没有范围、没有验收的指令，产出难以对齐预期。
2. **一次塞太多**：把十个不相关需求塞进一句话，容易顾此失彼；拆成清晰的步骤更好。
3. **不给上下文就怪答错**：不引用文件、不贴报错，模型只能猜。
4. **忽视边界声明**：不说明"哪些不能动"，可能改到不该改的地方。
5. **让 Agent 擅自提交**：`git commit` 等应由你显式发起，别默认它会替你做。
6. **记忆当圣旨**：记忆可能过时，最终以当前代码/配置和你的指令为准。
