# 5.5 AI 项目集成交付

> 模型跑通只是 20%，把它接进真实业务系统、通过验收、让一线用起来，才是剩下的 80%。本节讲 AI 项目从"能演示"到"进生产"的集成与交付方法。

## 学习目标

学完本节后，你将能够：

- [ ] 说清 AI 能力集成进企业现有系统的四种主要模式
- [ ] 设计大模型应用与 ERP/CRM/工单/知识库等系统的集成架构
- [ ] 制定 AI 项目的交付物清单与验收标准
- [ ] 处理数据集成、权限、安全与合规问题
- [ ] 规划上线灰度、用户采纳与变更管理
- [ ] 用交付检查清单做 Go-Live 前的最终核对

## 5.5.1 集成交付为什么是 AI 项目的"最后一公里"

PoC 阶段通常用一个独立 Demo 验证模型效果。要进入生产，AI 能力必须嵌入企业既有 IT 与业务流程：

```
PoC 阶段                          生产交付阶段
─────────                        ──────────────
单个 Notebook / 脚本      →       高可用服务 (SLA)
静态演示数据               →       实时业务数据（接 CRM/ERP/数据库）
工程师手动调用             →       一线人员在原系统里无感使用
效果"看着不错"             →       量化验收 + 监控 + 回滚
无权限/审计                →       数据权限、合规、审计日志
```

**交付失败的常见根因不是模型不准，而是**：没接进真实流程（一线要切换系统、多录一遍）、数据没打通（知识库是旧的）、没人对上线后效果负责、没有回滚预案。

## 5.5.2 四种集成模式

| 模式 | 形态 | 适用场景 | 交付重点 |
|------|------|----------|----------|
| **API 嵌入式** | 把大模型能力封装成内部 API，供现有系统调用 | 已有业务系统，加一个智能功能 | 接口稳定、延迟、降级、鉴权 |
| **RAG 知识助手** | 对接企业知识库/文档，做问答与检索 | 客服、内部知识、制度查询 | 知识同步、权限隔离、引用溯源 |
| **Agent 流程嵌入** | Agent 调用业务工具（查订单、建工单、改数据） | 自动化跨系统流程 | 工具接入、权限边界、人工确认 |
| **独立 AI 应用/门户** | 新建一个 AI 产品入口 | 新业务、对外服务 | 产品体验、账号、运营 |

选型原则：**能嵌入现有流程就不要让用户切换系统**。一线人员在工单系统里点一下就能用的 AI 助手，采纳率远高于一个独立聊天窗口。

### 典型集成架构

```
        一线用户（客服/销售/运营/员工）
                 │
        现有业务系统（CRM / 工单 / OA / IM）
                 │  内嵌调用 / 侧边栏 / 机器人
                 ▼
        ┌──────────────────────────────┐
        │      AI 应用服务层            │
        │  编排(Orchestration)          │
        │  提示模板 / RAG / Agent / 路由 │
        └───┬───────────┬──────────┬────┘
            │           │          │
     ┌──────▼──┐  ┌─────▼─────┐  ┌─▼──────────────┐
     │ 模型服务 │  │ 检索/向量库 │  │ 业务工具/API    │
     │(API/自建)│  │(企业知识库) │  │(订单/工单/数据库)│
     └─────────┘  └───────────┘  └────────────────┘
            │           │          │
        ┌───▼───────────▼──────────▼────┐
        │  数据层：数据仓库 / 文档 / 权限  │
        └───────────────────────────────┘
            │
     横切：监控 · 日志审计 · 成本 · 安全合规 · 评测
```

## 5.5.3 数据集成与治理

AI 项目的数据集成比传统项目更敏感，因为大模型会"读到"并可能"说出"数据内容。

| 事项 | 要求 |
|------|------|
| 知识同步 | RAG 知识库与源文档保持同步（定时增量更新），避免模型用过时内容作答 |
| 数据权限 | **检索时按用户权限过滤**，不能让普通员工检索到机密文档（行级/文档级 ACL） |
| 数据边界 | 明确哪些数据可以进提示、哪些禁止出域（敏感字段脱敏） |
| 私有化 | 强合规行业（金融/医疗/政务）数据不出内网，选私有部署或 VPC |
| 留痕 | 记录谁、何时、问了什么、模型答了什么、用了哪些知识，供审计 |
| 数据质量 | 交付前做数据审计：重复、过期、缺失、矛盾文档要清理 |

**关键反模式**：把所有文档一股脑向量化。结果是检索召回噪声大、答案互相矛盾、权限越界。知识库要做分域、分权、定期清理。

## 5.5.4 安全与合规

| 领域 | 交付要求 |
|------|----------|
| 访问控制 | 模型服务鉴权、与企业 SSO/账号体系打通、最小权限 |
| 内容安全 | 输入输出过审（敏感词、有害内容）、注入攻击防护（Prompt Injection） |
| 工具调用安全 | Agent 写操作（改数据、发消息）必须二次确认 + 权限校验 + 可回滚 |
| 数据合规 | 个人信息保护（PIPL/GDPR）、行业监管（金融/医疗）、数据不出域 |
| 模型溯源 | 重要结论给出来源引用，可追溯到具体文档 |
| 责任界定 | 高风险决策（授信、诊断、法律意见）AI 只做辅助，人工拍板 |

## 5.5.5 交付物与验收

### AI 项目交付物清单

| 类别 | 交付物 |
|------|--------|
| 软件 | 模型服务/API、AI 应用、集成接口、管理后台 |
| 数据 | 知识库/向量库、评测集、数据字典、标注规范 |
| 运维 | 部署文档、监控看板、告警规则、回滚预案、容量评估 |
| 质量 | 评测报告、压测报告、安全测评报告、验收用例 |
| 运营 | 用户手册、培训材料、FAQ、badcase 反馈与迭代机制 |
| 交接 | 运维 owner、二次开发文档、模型/提示版本记录 |

### 验收标准（必须可量化）

- **功能验收**：验收用例通过率（预先约定的一批真实场景）
- **效果验收**：核心质量指标达标（如问答命中率、人工采纳率），用双方确认的评测集
- **性能验收**：P95 延迟、并发量、可用性（如 99.9%）
- **成本验收**：单次调用成本、月度成本在预算内
- **安全验收**：权限越界测试、注入测试、敏感数据检测通过
- **试运行**：连续 N 天稳定运行，护栏指标无红线

> 验收标准必须在项目启动时就写进合同/SOW，而不是上线后再争论"效果好不好"。

## 5.5.6 上线策略与变更管理

### 灰度发布

```
内部测试 → 种子用户(10%) → 单部门(一个业务线) → 全量
   │            │                │                  │
 调试         收集 badcase     验证业务指标        全面推广
```

每一档都设**回滚开关**（feature flag），出问题一键切回原流程。

### 用户采纳（最容易被忽略）

AI 项目的 ROI 最终取决于一线用不用：

- **嵌入工作流**：在用户已有的系统里用，不要强迫切换
- **早期共创**：让一线骨干参与试点，他们成为内部推广者
- **培训与话术**：教用户怎么提问、何时信任、何时必须人工复核
- **激励与反馈**：建立"一键反馈 badcase"机制，让用户看到问题被修复
- **流程再造**：明确 AI 与人的分工（AI 起草、人审核），更新 SOP

### 交付后运营（不是终点）

- 设**长期 owner**（业务 + 技术），负责效果监控与迭代
- 建立 badcase → 评测集 → 优化的闭环
- 监控数据漂移、模型版本更新带来的回归
- 定期（如季度）做效果复盘与成本优化

## 常见误区

| 误区 | 正确理解 |
|------|----------|
| "模型准就交付了" | 集成、数据打通、权限、验收、培训才是交付主体 |
| "知识库把文档全塞进去" | 要分域、分权、定期同步清理，否则噪声大且越权 |
| "上线后项目就结束" | 模型会漂移，需长期 owner、监控、badcase 闭环 |
| "让用户去新系统用 AI" | 嵌入现有流程的采纳率远高于独立入口 |
| "Agent 可以直接改生产数据" | 写操作必须二次确认、权限校验、可回滚 |
| "验收时再谈效果标准" | 验收指标与评测集要在启动时写进 SOW |
