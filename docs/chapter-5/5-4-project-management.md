# 5.4 AI 项目管理与产品管理

> AI 项目和传统软件项目有本质差异：需求里掺着概率、交付物里掺着模型、进度里掺着数据。本节讲如何用一套适配 AI 特性的管理方法，把"模型效果不确定"这件事管起来。

## 学习目标

学完本节后，你将能够：

- [ ] 说清 AI 项目与传统软件项目在生命周期上的差异
- [ ] 用 PoC 驱动 + 双轨迭代的方式管理 AI 项目
- [ ] 搭建 AI 产品的指标体系（离线指标 / 在线指标 / 护栏指标）
- [ ] 划分 AI 团队角色并做 RACI 分工
- [ ] 管理 AI 项目特有的风险（效果不达标、数据、范围蔓延）
- [ ] 用健康度模型量化评估一个进行中的 AI 项目

---

## 5.4.1 AI 项目为什么不能套用传统管理

传统软件项目假设：需求可明确、实现可规划、结果可复现。AI 项目这三条都不成立：

| 维度 | 传统软件项目 | AI / 大模型项目 |
|------|--------------|------------------|
| 交付物 | 确定性功能（输入 A 必输出 B） | 概率性能力（输出分布，有错误率） |
| 进度风险 | 工程量、联调 | **模型效果能否达标**（最大不确定性） |
| 依赖 | 接口、人力 | 数据质量、数据量、标注、算力 |
| 验收 | 功能跑通即可 | 跑通 ≠ 有用，需统计指标达标 + 用户认可 |
| 迭代 | 改代码 | 改数据、改提示、改模型、改流程四选一或组合 |
| 维护 | 修 bug、加功能 | 数据漂移、模型衰减、持续评测 |

**核心结论**：AI 项目不能按"需求 → 开发 → 测试 → 上线"的瀑布一次性交付，必须按"假设 → 验证 → 再投入"的探索式节奏推进。最大的浪费是：在模型效果未被证明前，就投入大量工程和商务资源。

## 5.4.2 AI 项目生命周期

```
① 机会识别        ② PoC 验证          ③ 试点 (Pilot)       ④ 规模化          ⑤ 运营迭代
场景评估          最小模型跑通         真实业务小流量       全量上线          监控/再训练
可行性打分   →    核心指标验证   →    闭环流程跑通   →    集成/交付   →    数据/模型迭代
Go/No-Go         Go/No-Go            护栏指标建立         SLA 达成          漂移治理
(1-2 周)         (2-6 周)            (4-8 周)            (持续)            (持续)
```

每个阶段结束都要有一个 **Go/No-Go 决策门（Decision Gate）**，用预先约定的量化指标决定是否继续，而不是"做都做了"。

| 阶段 | 关键问题 | 通过门槛（示例） | 投入 |
|------|----------|------------------|------|
| PoC | 这事技术上做得到吗？ | 核心任务离线指标 ≥ 阈值（如问答命中率 70%） | 1-2 人，可全用 API |
| 试点 | 在真实流程里有用吗？ | 人工采纳率 ≥ 50%，无严重事故 | 小团队，接真实数据 |
| 规模化 | 扛得住业务量吗？ | 延迟/成本/稳定性达 SLA | 工程 + 运维到位 |
| 运营 | 效果会不会衰减？ | 漂移监控、季度评测、再训练机制 | 长期 owner |

## 5.4.3 PoC 驱动的迭代管理

### PoC 的纪律

- **一个 PoC 只验证一个最关键假设**。最常见的关键假设是"模型在我们的真实数据上效果够不够"，而不是"系统好不好用"
- **时间盒（Time-box）**：通常 2-6 周，到期必须给结论，不允许无限优化
- **用最便宜的方式证伪**：优先用大模型 API + 提示工程 + RAG，不要一上来就微调或自研
- **预先定义成功标准**：开做之前写清楚"指标到多少算成功"，避免事后挪球门

### 双轨 / 三轨迭代

AI 项目常并行三条工作轨，节奏不同：

| 轨道 | 内容 | 节奏 | 负责人 |
|------|------|------|--------|
| 数据轨 | 数据采集、清洗、标注、知识库建设 | 持续、前置 | 数据工程 / 标注 |
| 模型轨 | 提示、RAG、微调、评测集、效果迭代 | 按实验轮次 | 算法 / AI 工程 |
| 工程轨 | 服务化、集成、前端、稳定性、安全 | 按迭代（Scrum） | 后端 / 前端 |

管理要点：**模型轨用"实验"管理（假设-实验-结论），工程轨用"故事卡"管理（Scrum/Kanban）**，二者通过评审节奏对齐。不要把模型实验塞进固定两周的功能冲刺里。

## 5.4.4 AI 团队角色与 RACI

一个能落地的 AI 项目通常需要这些角色（小团队可一人多角）：

| 角色 | 职责 |
|------|------|
| AI 产品经理 | 定义场景、成功指标、优先级，管理业务方预期 |
| 算法 / AI 工程师 | 模型选型、提示/RAG/微调、评测、效果优化 |
| 数据工程师 | 数据管道、知识库、数据质量 |
| 后端 / 平台工程师 | 模型服务化、集成、MLOps、稳定性 |
| 业务专家（SME） | 提供领域知识、标注规范、验收 |
| 标注 / 运营 | 数据标注、badcase 回流 |

RACI 示例（R 负责 / A 批准 / C 咨询 / I 知会）：

| 活动 | AI PM | 算法 | 数据 | 工程 | 业务专家 |
|------|-------|------|------|------|----------|
| 场景优先级 | A/R | C | C | C | C |
| 评测集与验收标准 | A | R | C | I | R |
| 模型方案选型 | C | A/R | C | C | C |
| 数据标注规范 | C | C | R | I | A |
| 上线 Go/No-Go | A | R | C | R | R |
| 上线后效果运营 | R | C | C | C | R |

## 5.4.5 AI 产品指标体系

AI 产品最大的管理陷阱：**只盯模型指标，不盯业务结果**。模型准确率 95% 的功能可能没人用，准确率 80% 的功能可能因为节省一半时间而被高度采纳。

### 三层指标

| 层级 | 指标类型 | 例子 | 用途 |
|------|----------|------|------|
| 模型层（离线） | 任务质量 | 准确率、召回、BLEU/ROUGE、检索命中率、事实一致性 | 研发自测、版本对比 |
| 产品层（在线） | 用户行为 | 采纳率、改写率、人工接管率、任务完成率、留存 | 判断"有没有用" |
| 业务层（结果） | 价值 | 节省工时、转化率、客服工单下降、收入 | 算 ROI、要预算 |
| 护栏层（底线） | 风险 | 幻觉率、有害输出率、超时率、投诉率、成本/次 | 任何时候不能破 |

关键概念：

- **采纳率（Adoption Rate）**：AI 给的建议被用户直接采用的比例，是"有没有用"最直接的信号
- **人工接管率（Takeover / Escalation）**：AI 处理不了转人工的比例，越低越省人力
- **护栏指标（Guardrail Metrics）**：北极星指标涨的时候必须盯紧的底线指标。例如为了提升采纳率而放松安全审查，会让幻觉率上升
- **离线-在线鸿沟（Offline-Online Gap）**：评测集分数高不代表线上效果好，必须以线上 A/B 为准

### A/B 与灰度

- AI 功能上线用**灰度发布**：1% → 10% → 全量，每一档看护栏指标
- 对比组用"无 AI 的原流程"，衡量真实增量价值
- 大模型输出有随机性，评测要**多次采样取分布**，不能只看单次结果

## 5.4.6 范围与风险管理

### 范围管理

- **MoSCoW 优先级**：Must（核心场景闭环）/ Should（重要增强）/ Could（锦上添花）/ Won't（本期不做）。AI 项目尤其要克制，先把一个场景做穿
- **反模式："AI 万能"需求**：业务方要求"上一个智能助手什么都能干"。应拆成具体高频场景逐个交付
- 大模型能力边界清晰：不适合做高精度计算、强事务、零容错决策，这些留给传统系统

### AI 项目典型风险登记

| 风险 | 征兆 | 应对 |
|------|------|------|
| 效果不达标 | PoC 指标长期达不到阈值 | 降级为"AI 辅助 + 人工确认"；换更强模型；收窄场景 |
| 数据不足/质量差 | 知识库内容陈旧、标注不一致 | 提前做数据审计；数据工作前置；明确数据 owner |
| 成本失控 | 单用户 token 成本过高 | 缓存、小模型路由、压缩 prompt、限制调用频次 |
| 幻觉/合规事故 | 输出编造事实、违规内容 | RAG 接地、引用溯源、护栏、敏感场景强制人工 |
| 期望落差 | 业务方以为 AI 全自动 | 用 PoC 校准预期；明确"辅助"定位；早期就让业务方试用 |
| 范围蔓延 | 需求越加越多 | 时间盒 + MoSCoW + Decision Gate |

## 5.4.7 项目健康度评估

把"项目健不健康"从主观感觉变成量化分数。配套示例 `examples/5-4-pm/project_health.py`：

```python
# 六个维度，各 0-5 分，低于阈值给出预警
DIMENSIONS = {
    "效果进展":   "核心指标距离验收阈值有多远，是否有提升趋势",
    "数据就绪":   "评测集、训练/知识库数据是否齐备、质量如何",
    "工程就绪":   "服务化、集成、稳定性、监控是否到位",
    "业务对齐":   "业务方是否持续参与、验收标准是否一致",
    "进度风险":   "是否按里程碑推进，阻塞项是否及时清除",
    "成本风险":   "算力/API 成本是否在预算内",
}
```

运行后输出健康分与亮灯（绿/黄/红），用于周会和 Decision Gate。

## 常见误区

| 误区 | 正确理解 |
|------|----------|
| "把 AI 功能当普通功能排期" | 模型效果是最大不确定项，必须先 PoC 证伪再投入工程 |
| "准确率高 = 项目成功" | 要看业务层指标和采纳率，离线高分可能没人用 |
| "PoC 跑通就该全面上线" | PoC 只证明技术可行，试点要证明真实流程里的价值与 SLA |
| "需求一次性定死" | AI 需求要在数据和效果反馈中迭代，用双轨节奏管理 |
| "上线就结束了" | 模型会漂移衰减，需要持续评测、监控、再训练的长期 owner |
